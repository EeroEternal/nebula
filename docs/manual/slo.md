# 告警与故障处理

当监控提示「错误多了、变慢了、某台机器不健康」时，按本文排查。阈值可在 [`observability.md`](./observability.md) 里了解背景；Prometheus 规则见 `deploy/observe/prometheus-alerts.yml`。

---

## 先记住两条规则

1. **算服务故障的**：返回 5xx 等服务器错误。  
2. **不算服务故障的**：用户自己取消请求、正常升级前「排空」副本。

这样就不会把「用户关页面」误判成「服务挂了」。

---

## 我们在盯哪些指标

| 指标 | 白话含义 |
|------|----------|
| 请求成功率 | 100 次里有多少次是服务器正常答复 |
| 重试成功率 | 换副本重试后，有多少次救回来了 |
| 熔断次数 | 系统暂时不再往坏副本派活的次数 |
| 首 token / 总延迟 | 快慢 |
| 引擎健康采集 | 能不能读到 GPU 上推理程序的实时状态 |

控制台 **网关观测** 页的数据来自路由器汇总。

---

## 常见告警怎么处理

### 错误率突然升高（High5xx）

1. 打开控制台网关观测，看错误主要在「连不上」「超时」还是「引擎自己报 5xx」。  
2. 到 **端点 / 节点** 页看有没有副本不健康或刚做过升级。  
3. 用请求编号在日志和 trace 里查，定位是网关、路由器还是某台 GPU 机器。  
4. 若是单台坏：可先 **排空（Drain）** 该副本或回滚版本。  
5. 若是刚做过正常下线：短时间的波动可能是预期现象。

### 重试几乎都不成功

说明换副本也救不回来，往往是**所有副本或底层依赖**有问题，按上面 High5xx 做全量排查。

### 熔断次数突然变多

系统认为多台副本不可靠。查 GPU 显存是否打满、推理程序是否 OOM、是否正在批量重启。

### 超时特别多

区分：用户侧慢消费（取消多、abort 高） vs 引擎真慢（排队长、KV 缓存满）。后者考虑扩容或减少入口流量。

### 读不到引擎状态

路由器还能转发，但「谁最闲」的判断会变差。优先恢复推理程序自带的 metrics 页面能否访问。

## 建议的服务目标（需按业务调整）

| 目标 | 参考值 |
|------|--------|
| 长期可用性 | 99% 以上（即 5xx 低于 1%） |
| 短期告警 | 5 分钟内 5xx 超过 2% 就通知 |
| 小模型首 token | p95 约 2 秒内（仅作参考） |

流量很低时（例如长时间不到 1 次/秒），比例类告警容易误报，上线一两周后应结合实际调阈值。

---

## 上线前可做的演练

- 故意让一台副本报错：应触发告警，且流量逐渐绕开它。  
- 模拟用户取消：取消计数上升，但 5xx 不应上升。  
- 正常排空一台机器：不应出现长时间 5xx 尖峰。

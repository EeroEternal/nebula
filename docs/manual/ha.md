# 高可用（多副本）

让 **网关、控制台后台、路由器** 等控制面组件各跑至少两份：一台挂了，另一台还能对外服务。GPU 上的推理程序仍在各 GPU 机器上单独部署。

使用仓库里的 `docker-compose.ha.yml` 做演练；单机入门见 [`deployment.md`](./deployment.md)。

---

## 架构长什么样

| 部分 | 做什么 | 建议份数 |
|------|--------|----------|
| etcd | 存所有配置和状态 | 3 台（少一台仍能工作） |
| gateway / bff / router | 对外 API 与控制台 | 各 2 台 + 前面负载均衡 |
| scheduler | 决定模型放在哪台机器 | 2 台（同时只有 1 台「主」在写） |
| postgres | 控制台用户数据 | 1 台（更高可用可后续加） |
| node + 推理引擎 | 真正算模型 | 在 GPU 服务器上，不在此 compose 里 |

对外常用端口：网关 `8081`，控制台后台 `18090`，路由器 `18081`。

---

## 怎么启动演练环境

```bash
export OBSERVE_AUTH_MODE=internal   # 生产请用 service 并配置令牌

docker compose -f docker-compose.ha.yml up -d --build
docker compose -f docker-compose.ha.yml ps
```

etcd 地址可写成多台：`http://etcd1:2379,http://etcd2:2379,http://etcd3:2379`。

健康检查：三个 `/healthz`（或控制台 `/api/healthz`）应返回正常；调度器只有当前「主」节点返回 200。

---

## 建议做的故障演练

**停一台网关 / 控制台 / 路由器**  
负载均衡地址应仍能访问；再启动停掉的那台。

**停一台 etcd**  
控制台和部署操作应仍可用（剩余多数 etcd 正常）；再启动停掉的那台。

**停当前主的调度器**  
约十几秒内应选出新的主；旧主恢复后不应再擅自写配置（防脑裂）。

**停某 GPU 机器上的 node**  
只影响该机器上的模型副本；若配置了多副本或允许重调度，服务可恢复。

---

## 怎样算通过

- 任意**一台**接入层机器故障，用户仍能调 API、开控制台  
- 任意**一台** etcd 故障，配置读写正常  
- 调度器主备切换后，不会出现两份互相矛盾的部署指令  
- 故障期间能在监控里看到错误率和恢复时间  

详细验收记录可参考 [`../dev/ha/report.md`](../dev/ha/report.md)。

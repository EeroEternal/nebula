# Nebula 是做什么的

Nebula 帮企业在**自己的服务器和 GPU** 上，统一管理和对外提供大模型推理服务。

你可以把它理解成「推理机房的管家」：

- **模型怎么部署、扩几份、停哪一份** — Nebula 在控制台里点选或配置即可  
- **对外怎么调用** — 提供统一的 API 入口、登录鉴权、操作记录  
- **出问题怎么查** — 控制台里看请求量、错误、延迟；需要时可对接公司现有的监控和日志系统  

Nebula **不负责**训练模型，也**不是**帮你在网上代调 OpenAI 等云 API 的聚合网关。它管的是跑在你机房里的推理程序（例如 vLLM、SGLang）。

---

## 适合谁用

- 需要自建大模型服务的平台 / 基础设施团队  
- 私有化交付、要在客户机房落地推理能力的 ISV  
- 日常要盯服务是否健康、谁在用、用了多少的运维与产品同学  

---

## Nebula 和推理引擎怎么分工

| 谁来做 | 做什么 |
|--------|--------|
| **推理引擎**（vLLM、SGLang 等） | 真正跑模型、算 token、在单集群里做细粒度路由 |
| **Nebula** | 决定在哪些机器上起哪些模型、几个副本；统一对外入口；权限、审计、监控、租户与成本 |

用户请求的大致路径：**调用方 → Nebula 网关 → Nebula 路由器 → 某台机器上的推理引擎**。

若客户已有引擎自带的复杂集群（例如预填/decoding 分离），Nebula 只接它的**统一入口**，不替客户改引擎内部的机器编排。

---

## 控制台里能做什么

| 功能 | 你能做什么 |
|------|------------|
| 模型服务 | 部署、扩容、停止模型；看副本是否在跑 |
| 模型目录 / 模型库 | 从 Hugging Face 等源下载模型；管理已下载文件 |
| 网关 / 推理观测 | 看请求量、错误率、快慢、是否被限流 |
| 治理 | 查镜像和硬件是否匹配、服务是否达标、试用新版本、租户配额与费用 |
| Serving Cell | 登记外部推理集群入口，统一纳管观测（不改对方内部机器） |
| 审计日志 | 查谁在什么时间做了什么操作 |
| 节点与 GPU | 看有哪些机器、显卡是否在线、显存占用 |

# Nebula 是做什么的

面向产品经理、客户与交付同学：一眼看清 Nebula **是什么、有哪些模块、当前能做什么、哪些还不在交付范围**。

当前版本：**v1.3.0**。

---

## 背景：Nebula 管什么

企业把大模型跑在自己机房的 GPU 上时，通常还要自己解决这些事：模型文件从哪下、装在哪台机器、对外怎么调 API、谁有权限、坏了怎么发现、不同业务线怎么限额和算账。

Nebula 把这些事收成一套平台，帮企业在**自己的服务器和 GPU** 上统一管理和对外提供大模型推理服务。真正「算答案」的仍是机房里的推理程序（目前主要支持 **vLLM**、**SGLang**）；Nebula 负责管理、接入、观测和治理。

可以把它想成「推理机房的管家」：

- **模型怎么部署、扩几份、停哪一份** — 控制台里点选或配置即可
- **对外怎么调用** — 统一 API 入口、登录鉴权、操作记录
- **出问题怎么查** — 控制台看请求量、错误、延迟；需要时可对接公司现有监控和日志

Nebula **不负责**训练模型，也**不是**帮你在网上代调 OpenAI 等云 API 的聚合网关。

---

## 适合谁用

平台 / 基础设施团队要自建大模型服务；ISV 要私有化交付到客户机房；运维与产品同学日常要盯服务是否健康、谁在用、用了多少。

---

## 和推理引擎怎么分工

| 谁来做 | 做什么 |
|--------|--------|
| **推理引擎**（vLLM、SGLang 等） | 真正跑模型、算 token、在单集群里做细粒度路由 |
| **Nebula** | 决定在哪些机器上起哪些模型、几个副本；统一对外入口；权限、审计、监控、租户与成本 |

用户请求大致路径：**业务系统 → 网关 → 路由器 → 某台机器上的推理引擎**。  
运维在控制台的操作走另一条管理通道，**不会挤占**用户提问的主路。

## 功能模块一览

| 模块 | 通俗说法 | 主要作用 |
|------|----------|----------|
| **控制台** | 网页操作台 | 登录后点选部署、看机器与监控、做治理，不用记一堆命令 |
| **模型目录 / 模型库** | 找模型、管文件 | 从网上搜索下载模型；查看本机已有哪些模型文件、占多少盘 |
| **模型服务** | 把模型跑起来 | 指定跑几个副本、扩容/缩容/停止；看服务是否健康 |
| **网关** | 对外大门 | 统一 API 入口：验身份、记操作、限流；兼容常见调用格式（如 OpenAI） |
| **路由器** | 分诊台 | 把请求分到当前最合适的模型实例；坏实例会暂时避开并换一台重试 |
| **节点与 GPU** | 机房资产视图 | 看有哪些机器、显卡是否在线、显存大概占用多少 |
| **镜像与兼容** | 「这套软件能不能装到这台卡上」 | 登记推理软件包；部署前检查引擎版本与硬件是否匹配，避免装错 |
| **观测与告警** | 好不好用、出了啥问题 | 看请求量、错误、快慢；可对接公司监控/日志；可设服务目标（SLO） |
| **试用与选型（Benchmark / Canary）** | 先测再选、小流量试新版 | 用标准压测对比方案；推荐有依据；新版本可先小流量试用，不行就回退 |
| **多租户与成本** | 多业务线共用一套平台 | 按租户限额、看用量与费用；关掉此功能时仍可单令牌简单使用 |
| **高可用** | 大门别单点挂掉 | 网关/路由器可多副本；主控可切换，降低单机故障影响 |

各模块怎么用、出问题怎么办见 [`module.md`](./module.md)。

## 术语速查

| 说法 | 是什么意思 |
|------|------------|
| **推理 / 推理服务** | 模型根据提问生成回答的在线服务（不是训练） |
| **推理引擎** | 真正跑模型的程序，如 vLLM、SGLang |
| **副本** | 同一模型开多份实例，用来抗流量、互备 |
| **部署** | 指定「跑哪个模型、用什么配置、要几份」，平台负责落到机器上 |
| **缩容排空（Drain）** | 减副本时先让旧实例不再接新请求、把手头请求做完再关，减少打断用户 |
| **网关 / 路由器** | 见上表：大门负责身份与规范，分诊台负责选哪台实例 |
| **令牌（Token，访问用）** | 调用 API 时的身份凭证；可绑定角色，也可绑定租户 |
| **租户** | 平台上的一个业务方或客户方，可单独限额与看用量 |
| **镜像** | 打包好的推理软件环境（版本固定），便于在节点上预装与切换 |
| **兼容矩阵** | 「某引擎某版本 + 某类 GPU」是否允许一起用的规则表 |
| **观测** | 指标、链路追踪、日志：用来回答「现在怎么样、刚才哪一步慢/错了」 |
| **SLO（服务目标）** | 事先约定的达标线，例如延迟、可用性；平台可对照评估是否达标 |
| **Benchmark（基准测试）** | 用固定题目与条件测快慢、吞吐、错误率，便于公平对比 |
| **Canary（灰度试用）** | 新配置/新版本先接一小部分流量，达标再放大，不行就回退 |
| **高可用** | 关键组件挂了，整体服务尽量还能继续对外 |

## 当前已经能用的能力

### 装模型、跑服务

在控制台从 Hugging Face、ModelScope 等搜索并下载模型；在模型库查看已下载文件。  
声明「要跑哪个模型、几份」后，平台自动放到合适机器上启动，并检查是否健康；异常可自愈。支持多副本，也可按排队与显存压力自动加减份数。缩容时会尽量先排空再关。

### 对外提供统一 API

业务侧用常见大模型 API 格式（以 OpenAI 兼容为主，也可适配其他常见格式）访问一个入口即可。平台负责验身份、记审计、限流。请求会分到当前更空闲或更合适的实例；某实例连续出错会暂时屏蔽并换实例重试，减轻「一台坏了全挂」。

### 看机器与硬件

控制台可查看节点列表、GPU 是否在线、显存占用，以及卡型、驱动等基础信息，便于盘点机房资产。

### 避免「软件装错卡」

可登记推理软件包，并在部署前按规则检查：这套引擎/版本能不能装到目标硬件上。不匹配会明确拒绝并说明原因，而不是启动失败后才发现。也可锁定某个软件版本并记录为何强制覆盖。

### 看清引擎能干什么

对 vLLM、SGLang，平台知道常见能力边界；配置不合理会在部署前拦住。未知引擎类型会直接报错，不会悄悄当成别的引擎启动。运行起来后，控制台可展示探测到的能力信息。

### 监控、达标与排障

可看请求量、错误、延迟等；可对接公司现有监控与日志。可为模型设定服务目标并评估是否达标；流量太少时会标明「数据不足」，避免看起来「假绿」。可看与部署、放置、达标相关的诊断时间线。主动停机排空、用户取消请求等，不会当成「服务错误」去误伤达标统计。

### 选型、试用新版本

可用标准压测脚本对比不同方案；推荐结果会带来依据，证据不足时会明确说「数据不够」，不会瞎选默认引擎。新版本可先小流量试用，不达标可停止放量并回退。

### 多业务线共用与算账

可按租户设置请求频率、并发、用量与可访问模型等限额；可看用量与费用汇总；拒绝与配额相关操作会进审计。不需要多租户时保持简单的单令牌模式即可。

### 控制台与权限

网页控制台支持中英文；覆盖模型、机器、观测、审计、治理等日常操作。管理操作与用户提问走不同通道，互不影响。

### 关键组件可多开一份

网关、路由器可多副本部署，降低「大门挂了全站不可用」的风险。详见 [`module.md`](./module.md)「高可用」。

## 还在完善或尚未作为产品交付的

| 方向 | 现状（人话） |
|------|----------------|
| 监控达标 | 目标设定与评估、告警说明已有；用真实大流量「烧」一遍、告警实打实触发的验收仍在补 |
| 压测与灰度 | 流程与页面已有；多引擎、多模型在真机上反复跑通仍在补 |
| 多租户 | 限额与费用视图已有；大规模隔离压测仍在补 |
| 硬件历史趋势 | 当前偏「此刻库存」；长期利用率曲线库尚未交付 |
| 更多推理引擎 | 目前主推 vLLM / SGLang；其他引擎需有明确客户场景后再纳入 |
| 超大模型跨多机切分 | 单机装不下时才需要；按需开启，当前未作为通用能力交付 |
| 更深一层协议适配 | 默认直接对接引擎自带 HTTP；特殊协议增强按需，尚未作为通用产品能力 |
| 控制台增强 | 如模型预热等更顺手的产品化界面，单独排期 |
| 模型文件高级运维 | 控制台内不做自动清旧模型、整批机器间搬文件等复杂运维编排 |

配置中心「多机高可靠集群」的生产迁移当前暂缓；接入面多副本不依赖这一项。

---

## 明确不在产品主线里的事

不训练模型；不替你聚合调用公有云大模型 API。  
不以「纳管外部已有推理集群」作为产品能力对外承诺（接口与拓扑因引擎而异，不确定性高）。  
不以「另起一套监控替代公司现有 Prometheus」或「应用直接写日志库」为主路径。  
不为了多租户把每个租户细节塞进监控标签，避免监控爆炸（明细走审计与追踪查询）。

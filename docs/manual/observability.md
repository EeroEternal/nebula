# 监控与日志

帮你看清「服务好不好、慢在哪里、谁在用」——既能在 Nebula 控制台里看，也能接到公司现有的 Grafana、日志平台。

相关文档：出问题怎么办见 [`slo.md`](./slo.md)；日志怎么收集见 [`loki.md`](./loki.md)；网关配置见 [`gateway.md`](./gateway.md)。

---

## 三种信息，各看各的

| 看什么 | 用什么 | 适合谁 |
|--------|--------|--------|
| **一次对话的详情**（用了哪个模型、多慢、多少 token） | 内置观测服务 xtrace + 控制台 | 产品、运维排障 |
| **曲线图**（请求量、错误率、延迟趋势） | Prometheus 指标（可接 Grafana） | 运维、SRE |
| **文字日志**（某次请求在哪一步报错） | JSON 日志 → Loki / ELK | 运维深挖 |

三者用**同一个请求编号**（`request_id` / `trace_id`）串起来：在控制台看到异常后，可以按编号去日志里搜同一次请求。

```
各组件 → xtrace（对话级详情）
      → /metrics（给 Grafana 拉曲线）
      → 标准输出 JSON 日志（给日志平台采集）

控制台 ← 后台服务 ← 汇总上述数据
```

---

## 在控制台里怎么看

打开 **网关观测** 或 **推理** 页，重点看：

- **请求量**：有没有突然掉零或暴涨  
- **5xx 错误**：服务器自身出错的比例（用户中途取消不算在这里面）  
- **重试是否有效**：单台机器坏了时，系统有没有自动换别的副本  
- **延迟 / 首 token 时间**：用户体感快不快  

治理页里的 **模型 SLO** 会告诉你某个模型在设定目标下是否达标；流量太少时不会显示「假绿灯」。

## 和公司现有监控怎么配合

| 你的情况 | 建议 |
|----------|------|
| 只用 Nebula 控制台 | 配好 xtrace 地址和令牌即可（见 [`deployment.md`](./deployment.md)） |
| 已有 Grafana | 让 Prometheus 定期抓取各组件的 `/metrics` 地址 |
| 已有 Loki / 日志中心 | 各组件设置 `NEBULA_LOG_FORMAT=json`，用采集器收标准输出 |

注意：不要让控制台绕过后台直接去连 xtrace；不要把完整对话内容默认打进普通日志（审计有单独通道）。

## 几个名词

- **5xx**：服务端错误，算进「服务不可用」统计。  
- **Abort / 客户端断开**：用户取消或网络断了，**不算**服务故障。  
- **Drain（排空）**：升级前让某副本把手头请求做完再下线，正常收尾**不算**故障。  
- **TTFT**：从发出请求到收到第一个 token 的时间，用户感知的「起笔快慢」。  

告警默认参考（需按实际流量调整）：5 分钟内错误率超过 2%、重试几乎全失败、超时占比过高等。细则见 [`slo.md`](./slo.md)。

## 实施参考：环境变量

| 变量 | 含义 |
|------|------|
| `OBSERVE_URL` | xtrace 观测服务地址 |
| `OBSERVE_TOKEN` | 访问 xtrace 的令牌 |
| `OBSERVE_AUTH_MODE` | `internal`（内网免令牌）或 `service`（必须配令牌） |
| `NEBULA_LOG_FORMAT=json` | 输出结构化日志，便于 Loki 等采集 |

Prometheus 告警规则样例在仓库 `deploy/observe/prometheus-alerts.yml`。

# Nebula 功能模块

各模块「是什么、日常怎么用、出问题怎么办」。产品全景见 [`positioning.md`](./positioning.md)；怎么安装见 [`deployment.md`](./deployment.md)。

---

## 模型目录、模型库与模型服务

**模型目录**：从网上（Hugging Face、ModelScope）搜索并下载模型到机房。  
**模型库**：看已经下载到哪些机器、占多少空间。  
真正「跑起来提供服务」在 **模型服务** 页完成；目录/库管的是文件资产，服务页管的是运行中的副本。

典型流程：目录搜索下载 → 模型库出现记录 → 模型服务部署。删除前先确认服务里没有还在跑的副本，再在模型库删缓存。

| 页面 | 关注点 |
|------|--------|
| 模型目录 | 找模型、触发下载 |
| 模型库 | 已下载文件、路径、是否在磁盘上 |
| 模型服务 | 副本数、是否在跑、健康状态 |

控制台内不做：自动清旧模型、整批机器间搬文件、复杂异步编排（需运维或脚本）。接口走 `/api/v2/models/*`；存储路径可在下载对话框指定，留空则用节点默认目录。

## 网关与路由器

对外 API 的「大门」和「分诊台」：先验身份、记日志，再把请求分到合适的模型实例。

| 组件 | 通俗说法 | 主要工作 |
|------|----------|----------|
| **Gateway（网关）** | 大门保安 + 前台 | 校验访问令牌、限流、记审计；支持多种 API 格式；**不决定**进哪台机器 |
| **Router（路由器）** | 分诊台 | 看哪台模型实例最空闲，把请求转过去；失败时重试、暂时屏蔽坏实例 |

```
调用方 → 网关 → 路由器 → 某台 GPU 上的推理程序
              ↘ 控制台后台（管模型，不走推理主路）
```

网关能力：登录与权限（令牌可绑租户、可限每分钟次数）、操作记录、协议转换（OpenAI / Anthropic 等）、监控数据双写。  
路由器能力：自动同步实例列表、优先分给排队最少的副本、连续出错暂时屏蔽并可换副本重试。

**日常运维：** 改配置或发版时先动路由器、观察约半小时，再动网关。成功标准：正常提问有回答；单机故障时重试/熔断计数可上升，但整体错误率不应长期恶化。需要回滚时可先关掉路由器自动重试止血，或换回上一版并确认健康检查通过。控制台「网关观测」看汇总；告警处理见下文「告警与故障处理」。

### 实施参考：常用环境变量

| 变量 | 含义 |
|------|------|
| `NEBULA_GATEWAY_ADDR` | 网关监听地址，默认 `8081` |
| `NEBULA_ROUTER_URL` | 路由器地址 |
| `NEBULA_AUTH_TOKENS` | 访问令牌，格式 `令牌:角色` 或 `令牌:角色:租户` |
| `NEBULA_AUTH_DISABLED` | 仅开发环境：关闭鉴权 |
| `NEBULA_MULTI_TENANT` | 开启后按租户配额限流 |
| `NEBULA_AUTH_RATE_LIMIT_PER_MINUTE` | 每令牌或租户每分钟请求上限 |
| `NEBULA_LOG_FORMAT=json` | 建议生产开启，便于收集日志 |
| `NEBULA_ROUTER_RETRY_MAX` | 失败时最多换几个副本重试 |
| `NEBULA_ROUTER_RETRY_BACKOFF_MS` | 重试间隔（毫秒） |
| `NEBULA_ROUTE_CIRCUIT_FAILURE_THRESHOLD` | 连续失败多少次后暂时屏蔽该副本 |
| `NEBULA_ROUTE_CIRCUIT_OPEN_MS` | 屏蔽多久后再尝试 |

完整列表与默认值见 [`deployment.md`](./deployment.md) 与 `deploy/nebula.env.example`。

## 控制台后台（BFF）

**BFF** = Backend for Frontend：专门为控制台网页提供 API（进程 `nebula-bff`，默认端口 `18090`）。浏览器里的部署、扩容、看机器与监控，大多由它处理；**不替代**用户推理时走的网关 → 路由器 → 引擎主路径。

| 你在页面上… | 后台在管… |
|-------------|-----------|
| 登录、改密码 | 用户与会话（PostgreSQL） |
| 模型服务：部署 / 停止 / 扩容 | 模型部署期望，交给调度器执行 |
| 模型目录 / 模型库 | 下载任务、已下载文件、存储路径 |
| 治理 | 兼容规则、硬件清单、SLO、试用版本、租户与费用 |
| 网关观测 / 推理 / 审计 | 从观测系统汇总数据展示 |

```
浏览器 → BFF → 配置库（etcd）→ 调度器 / 节点 真正起停模型
            → 数据库（用户与设置）
            → 观测系统（图表与审计）
```

用户调 API 问模型 → 走 Gateway；控制台点「部署模型」→ 走 BFF。两条路互不影响。

观测鉴权：`OBSERVE_AUTH_MODE=internal` 适合内网开发（可不配令牌）；`service` 适合生产（必须配 `OBSERVE_TOKEN`）。审计页报 Unauthorized，多半是观测令牌未配或与 xtrace 不一致，检查步骤见 [`deployment.md`](./deployment.md) 第 5 节。控制台 API 前缀一般为 `/api/v2/...`。

## 监控与日志

帮你看清「服务好不好、慢在哪里、谁在用」——既能在控制台里看，也能接到公司现有的 Grafana、日志平台。

| 看什么 | 用什么 | 适合谁 |
|--------|--------|--------|
| **一次对话的详情**（模型、快慢、token） | 内置观测服务 xtrace + 控制台 | 产品、运维排障 |
| **曲线图**（请求量、错误率、延迟） | Prometheus 指标（可接 Grafana） | 运维、SRE |
| **文字日志**（某次请求在哪一步报错） | JSON 日志 → Loki / ELK | 运维深挖 |

三者用同一个请求编号（`request_id` / `trace_id`）串起来。

```
各组件 → xtrace（对话级详情）
      → /metrics（给 Grafana 拉曲线）
      → 标准输出 JSON 日志（给日志平台采集）

控制台 ← 后台服务 ← 汇总上述数据
```

控制台 **网关观测 / 推理** 页重点看：请求量是否掉零或暴涨、5xx 比例（用户取消不算）、重试是否有效、延迟 / 首 token。治理页 **模型 SLO** 会告诉你是否达标；流量太少时不会显示「假绿灯」。

| 你的情况 | 建议 |
|----------|------|
| 只用 Nebula 控制台 | 配好 xtrace 地址和令牌（见 [`deployment.md`](./deployment.md)） |
| 已有 Grafana | 让 Prometheus 定期抓取各组件 `/metrics` |
| 已有 Loki / 日志中心 | 设 `NEBULA_LOG_FORMAT=json`，用采集器收标准输出 |

不要让控制台绕过 BFF 直接连 xtrace；不要把完整对话内容默认打进普通日志（审计有单独通道）。

几个名词：**5xx** 算服务故障；**Abort / 客户端断开**与正常 **Drain（排空）**不算；**TTFT** 是发出请求到首个 token 的时间。

### 日志收集（Loki 等）

各组件把 JSON 行写到标准输出；由 Promtail、Vector 等收走再存进 Loki / ELK。**程序本身不会直接连 Loki。**

```bash
export NEBULA_LOG_FORMAT=json
```

示例配置：`deploy/observe/promtail-nebula.yaml`、`deploy/observe/vector-nebula.toml`。在 Loki 里按 `request_id` 搜：

```logql
{job="nebula"} | json | request_id="req_xxxxxxxx"
```

排障路径：控制台看 trace → 复制 request_id → Loki 看详细日志 → 需要曲线时去 Grafana。

### 实施参考：观测环境变量

| 变量 | 含义 |
|------|------|
| `OBSERVE_URL` | xtrace 观测服务地址 |
| `OBSERVE_TOKEN` | 访问 xtrace 的令牌 |
| `OBSERVE_AUTH_MODE` | `internal`（内网免令牌）或 `service`（必须配令牌） |
| `NEBULA_LOG_FORMAT=json` | 输出结构化日志，便于 Loki 等采集 |

Prometheus 告警规则样例：`deploy/observe/prometheus-alerts.yml`。

## 告警与故障处理

先记住：算服务故障的是 5xx 等服务器错误；用户自己取消、正常升级前排空副本**不算**故障。

| 指标 | 白话含义 |
|------|----------|
| 请求成功率 | 100 次里有多少次是服务器正常答复 |
| 重试成功率 | 换副本重试后，有多少次救回来了 |
| 熔断次数 | 系统暂时不再往坏副本派活的次数 |
| 首 token / 总延迟 | 快慢 |
| 引擎健康采集 | 能不能读到 GPU 上推理程序的实时状态 |

**错误率突然升高（High5xx）：** 控制台看错误类型（连不上 / 超时 / 引擎 5xx）→ 端点/节点页看副本是否不健康或刚升级 → 用请求编号查日志与 trace → 单台坏可 Drain 或回滚；刚做过正常下线时短波动可能是预期。

**重试几乎都不成功：** 往往是所有副本或底层依赖有问题，按 High5xx 全量排查。  
**熔断次数突然变多：** 查显存是否打满、推理程序是否 OOM、是否正在批量重启。  
**超时特别多：** 区分用户侧慢消费（abort 高）vs 引擎真慢（排队长、KV 满）；后者考虑扩容或减入口流量。  
**读不到引擎状态：** 路由器还能转发，但选闲实例会变差；优先恢复引擎 metrics 页面可达。

建议服务目标（需按业务调整）：长期可用性 99% 以上；5 分钟内 5xx 超过 2% 告警；小模型首 token p95 约 2 秒内（仅参考）。流量很低时比例类告警易误报，上线一两周后应结合实际调阈值。

上线前可演练：故意让一台副本报错（应告警并绕开）；模拟用户取消（取消计数升、5xx 不升）；正常排空一台（不应长时间 5xx 尖峰）。

## 高可用（多副本）

让网关、控制台后台、路由器等控制面各跑至少两份：一台挂了，另一台还能对外服务。GPU 上的推理程序仍在各 GPU 机器上单独部署。演练用 `docker-compose.ha.yml`；单机入门见 [`deployment.md`](./deployment.md)。

| 部分 | 做什么 | 建议份数 |
|------|--------|----------|
| etcd | 存所有配置和状态 | 3 台（少一台仍能工作） |
| gateway / bff / router | 对外 API 与控制台 | 各 2 台 + 前面负载均衡 |
| scheduler | 决定模型放在哪台机器 | 2 台（同时只有 1 台「主」在写） |
| postgres | 控制台用户数据 | 1 台（更高可用可后续加） |
| node + 推理引擎 | 真正算模型 | 在 GPU 服务器上，不在此 compose 里 |

```bash
export OBSERVE_AUTH_MODE=internal   # 生产请用 service 并配置令牌
docker compose -f docker-compose.ha.yml up -d --build
docker compose -f docker-compose.ha.yml ps
```

etcd 可写成多台：`http://etcd1:2379,http://etcd2:2379,http://etcd3:2379`。健康检查：三个 `/healthz`（或控制台 `/api/healthz`）应正常；调度器只有当前「主」返回 200。

建议演练：停一台网关/控制台/路由器（负载均衡地址仍可用）；停一台 etcd（配置读写仍可用）；停当前主调度器（约十几秒选出新主，旧主恢复后不应再擅自写）；停某 GPU 上的 node（只影响该机副本，多副本或允许重调度时可恢复）。

生产要把单节点 etcd 切成三节点时，按 [`etcd-ha.md`](./etcd-ha.md)（多 `ETCD_ENDPOINT`、快照迁移、杀 1/3 演练）。详细验收见 [`../dev/ha/report.md`](../dev/ha/report.md)。

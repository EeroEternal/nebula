## 2. 产品定位

### 2.1 一句话

**Nebula 是面向本地 / 专有化 GPU 机房的跨引擎大模型推理控制面**：统一管理模型部署与生命周期，对外提供一致的 API，并完成权限、观测、多租户、成本与选型治理。真正「算 token」的仍是外部推理引擎（vLLM、SGLang、以及后续接入的 TRT-LLM、LMDeploy、llama.cpp 等）。

### 2.2 适合谁

| 角色 | 诉求 |
|------|------|
| 平台 / 基础设施团队 | 在自有 GPU 上统一起服务、统一入口、统一观测 |
| ISV / 私有化交付 | 交到客户机房的一套可运维控制面 |
| 运维与 SRE | 副本、故障、扩缩、审计、成本可管 |
| 业务方 | 只关心 OpenAI 兼容调用与 SLA，不关心后端引擎细节 |

### 2.3 明确不是什么

- **不是**训练平台
- **不是**公有云大模型 API 聚合网关
- **不是**引擎内部的 PD / worker / cache-aware 调度器
- **不是**用 Actor 内存态堆出来的进程编排器

### 2.4 与推理引擎的分工

| 谁 | 做什么 |
|----|--------|
| **推理引擎** | 单机或引擎原生分布式上的推理、细粒度 batch、KV、原生优化 |
| **Nebula** | 模型放哪、起几份、对外统一入口、鉴权审计、兼容与选型、SLO/成本/多租户、故障隔离与发布 |

请求主路径：

```text
业务系统 → Gateway（一致性接入）→ Router（按 Placement 选路）→ 引擎进程
控制与治理：控制台 / CLI → BFF → etcd 声明式期望 → Scheduler / Node
```

## 3. 建设目标

### 3.1 总目标

在**不推倒现有控制面主轴**（etcd 权威、声明式 Placement、Engine-Passthrough、Rust 控制面）的前提下，把 Nebula 建成企业可用的 **统一模型服务平台**，使客户能够：

> **声明模型、服务目标与资源约束 → 系统给出或执行合理的后端方案 → 用同一套 API 与运维面长期运行。**

### 3.2 目标能力组合（四层 + 底座）

平台能力按五层理解（底层为已有控制面底座）：

```text
┌────────────────────────────────────────────┐
│  L4  生产运维闭环                            │  监控·告警·容量·成本·审计·多租户·SLA
├────────────────────────────────────────────┤
│  L3  智能选择层                              │  架构/量化/硬件/并发/目标/成本 → 最优后端
├────────────────────────────────────────────┤
│  L2  异构调度与资源管理                      │  混部·池化·PD 分离·迁移·故障隔离·利用率
├────────────────────────────────────────────┤
│  L1  一致性抽象层                            │  统一 API·工具调用·流式·错误·KV 语义·生命周期
├────────────────────────────────────────────┤
│  L0  控制面底座（已有）                       │  Gateway·Router·Scheduler·Node·etcd·BFF
└────────────────────────────────────────────┘
```

| 层级 | 名称 | 要达到的目的 |
|------|------|----------------|
| **L0** | 控制面底座 | 声明式部署、可靠选路、引擎零侵入、状态可重建 |
| **L1** | 一致性抽象 | 客户写一次代码，后端可换；行为与错误可预期 |
| **L2** | 异构调度与资源 | 同一集群吃不同卡与拓扑，资源效率与隔离兼顾 |
| **L3** | 智能选择 | 在约束下选出（或建议）合适引擎/镜像/池，并算清切换代价 |
| **L4** | 生产运维闭环 | 可观测、可问责、可扩容规划、SLA 可运营 |

四层是**产品目标能力**；L0 是 Nebula 已经具备并坚持的工程主轴。L1–L4 在 L0 之上演进，禁止破坏 L0 原则。

## 4. 各层详细目标与职责

### 4.1 L0 — 控制面底座（现状巩固）

**目的**：让「部署、扩缩、选路、自愈」在私有化环境中正确、可审计、可 HA。

**已有要点**：

- Gateway：OpenAI 兼容、鉴权、审计、租户准入
- Router：按 Placement 代理、熔断重试
- Scheduler：Deployment → PlacementPlan（CAS）
- Node：启停引擎、注册 endpoint/capability、Drain
- etcd：唯一权威元数据
- 默认 Engine-Passthrough；BFF + 控制台

**演进要求**：真机 e2e、多租户压测、生产 etcd 路径、观测 burn —— 作为上层能力的质量门禁，而不是改架构。

---

### 4.2 L1 — 一致性抽象层

**目的**：屏蔽后端差异，形成稳定的「模型服务契约」。

**职责**：

| 维度 | 目标行为 |
|------|----------|
| API | 统一 OpenAI 兼容（及必要扩展），引擎方言在边界适配 |
| 工具调用 | 统一校验与解析；不支持则明确 `unsupported` |
| Streaming / Abort | 统一 SSE 与取消语义，契约测试强制 |
| 错误处理 | 稳定错误码（限流、不兼容、过载、上游故障等） |
| KV / 指标语义 | 对外统一字段与单位；引擎差异留在 Adapter scrape |
| 生命周期 | 创建/更新/停止/扩缩语义跨引擎一致（声明式 Deployment） |
| 能力发现 | Supported / Unsupported / Unknown 三态，禁止用 0 假装支持 |

**边界**：

- 一致性逻辑主要在 **Gateway + Adapter 契约**
- Router 不承担协议翻译与选型
- 不把引擎内部路由语义「统一」进 Nebula

**达到的目的**：业务与 SDK 与后端解耦；换引擎是平台动作，不是改客户代码。

---

### 4.3 L2 — 异构调度与资源管理层

**目的**：在真实机房「多厂商、多规格、多角色」约束下，把模型放到合适的资源上，并保持故障与利用率可控。

**职责**：

- **资源池（HardwarePool）**：按 platform / device_class / 角色（general、prefill、decode、edge）划分
- **混部**：同集群多池；Deployment 约束 `allowed_pools`；兼容矩阵硬过滤
- **拓扑**：`replicated` / `multi_node_tp` / `pd_split`（后两者按需、且依赖引擎原生能力）
- **故障隔离**：节点/池级移出候选；副本 Drain；避免跨池连带
- **动态迁移**：只通过新 Placement 版本 + 渐进切流（Canary），不做热路径原地搬进程
- **利用率**：在 pending/KV/GPU 信号上做扩缩与池水位，服务容量规划输入

**边界**：

- Nebula **放置与健康聚合**，不实现集合通信或引擎内部 PD worker 调度
- 跨节点 TP / PD 分离仅在引擎支持且矩阵允许时开放

**达到的目的**：一块控制面管理异构算力；资源能用尽、故障可挡、迁移可回滚。

---

### 4.4 L3 — 智能选择层

**目的**：在「模型 × 硬件 × 目标 × 成本」下，给出可解释的后端方案，并处理切换代价。

**输入（示意）**：

- 模型：架构（Dense/MoE）、量化、规模、上下文等（ModelProfile）
- 负载：并发、QPS、长短上下文比例等（WorkloadHint）
- 约束：SLO、预算、允许的引擎/池、偏好（延迟/吞吐/成本）
- 现状：当前 Deployment（用于计算切换成本）

**输出**：

- 有序 `BackendCandidate`：引擎、版本、镜像、池、拓扑、预估性能与成本
- `switching_cost`、`confidence`、`reasons`、证据 ID
- 证据不足 → `insufficient_data`，禁止静默默认引擎

**职责要点**：

- 硬过滤（兼容 + Capability）→ 证据召回（Benchmark Profile + 可选线上 SLI）→ 多目标打分 → 切换成本惩罚 → Top-K
- **默认半自动**（控制台确认后写 Deployment）；全自动仅开关 + 冷却 + 审计
- 落地路径：声明式 Deployment → 可选 Canary → 违约回滚

**边界**：

- **不在** Gateway/Router 热路径执行
- 不直接改 endpoint；只产生或建议期望状态
- 与 P5 关系：Benchmark/Canary 是证据与发布手段；本层是决策层

**达到的目的**：选型从「人肉经验 + 零散推荐」变为「约束下可解释、可回滚的平台能力」。

---

### 4.5 L4 — 生产运维闭环

**目的**：让平台在生产中「跑得久、说得清、算得过账、达得到约」。

**职责**：

| 能力 | 目标 |
|------|------|
| 监控与追踪 | 指标 + Trace + 日志可按 request_id 串联；热路径与观测解耦 |
| 告警与诊断 | SLO 评估不假绿；abort/Drain 不计错误预算；诊断时间线可下钻 |
| 容量规划 | 基于负载与画像给出缺口，而非盲目自动扩 |
| 成本归因 | 租户 × 模型 × 引擎 × 池；单位有效 token 成本；反哺选择层 |
| 审计 | 部署、选型、配额拒绝、自动动作可追溯 |
| 多租户 | 配额与准入在 Gateway 边界；租户互不影响（压测验证） |
| SLA 实质化 | 违约可解释 → 建议动作 → 可选半自动执行（演练后） |

**达到的目的**：平台从「能部署」变为「能运营、能问责、能规划」。

## 5. 总体架构关系（逻辑视图）

```text
                    ┌──────────── 控制台 / CLI / SDK ────────────┐
                    │              L3 选择  L4 治理视图            │
                    └──────────────────┬─────────────────────────┘
                                       │
                                       ▼
                                 BFF（控制面 API）
                                       │
           ┌───────────────────────────┼───────────────────────────┐
           │                           │                           │
           ▼                           ▼                           ▼
    Selection / Recommend        Deployments / Tenants        SLO / Audit / Cost
    (L3，非热路径)               Profiles / Pools             (L4)
           │                           │
           │                    声明式期望写入 etcd
           │                           │
           │                           ▼
           │                    Scheduler（L2 放置逻辑）
           │                           │
           │                           ▼
           │                    Node + HardwarePool
           │                           │
           │                           ▼
           │                    引擎进程（多后端）
           │                           ▲
           │                           │ Passthrough
           ▼                           │
    （不经过）              Gateway(L1) → Router → Engine
```

**数据面**：只走 L1 接入 + L0 选路。  
**控制面**：L3/L4 决策与治理 → 声明式状态 → L2 调度执行。

## 6. 与现状（v1.4.0）的映射

| 目标层 | 现状基础 | 主要缺口 |
|--------|----------|----------|
| L0 | 完整控制面 + Lite + 多租户 Batch1 | 真机 e2e、etcd 生产路径、压测证据 |
| L1 | OpenAI Gateway、Capability、部分协议适配 | 工具调用/错误码/流式契约强制化；多引擎一致性套件 |
| L2 | platform 过滤、兼容矩阵、单拓扑副本 | HardwarePool、PD/TP 拓扑、池级隔离与迁移规范 |
| L3 | P5 recommend + Canary | **独立选择层**、ModelProfile、切换成本、半自动闭环 |
| L4 | SLO/诊断/审计/成本/多租户 | 真机 burn、容量规划、SLA 动作闭环、历史利用率 |

结论：L0 可继续作为唯一主轴；L1–L4 是增量产品能力，其中 **L3 在现有设计文档中尚未成层**，需单独补设计并挂到总纲下。

## 7. 不可突破的设计原则

1. **控制面 / 执行面分离**；引擎零侵入，默认 Passthrough。
2. **etcd 唯一权威**；本地缓存可丢；禁止双权威 reconcile。
3. **一种状态一个 Owner**（Deployment / Placement / Endpoint 职责不交叉）。
4. **智能与重治理永不进入推理热路径**。
5. **无证据不自动选型**；数据不足显式返回。
6. **切换必声明式、可 Canary、可回滚**；禁止静默换引擎。
7. **异构只做放置与健康**，不接管引擎内部 PD/worker。
8. **观测失败不影响 token 流**；高基数信息不进 Prometheus label。
9. **不训练、不聚合公有云 API、不 Actor 回潮**。

## 8. 演进路线（与能力层对齐）

| 阶段 | 重点 | 对应层 | 目的 |
|------|------|--------|------|
| **Phase 0** | 真机 e2e、多租户压测、观测 burn、etcd HA runbook | L0/L4 地基 | 上层功能可证明 |
| **Phase 1** | 一致性契约套件；ModelProfile；Selection 推荐+草稿；控制台选型向导 | L1 + L3 骨架 | 写一次代码可换后端的前提 + 可解释选型 |
| **Phase 2** | HardwarePool、池约束、PD/TP（按需）、故障隔离规范 | L2 | 异构资源可调度 |
| **Phase 3** | SLO→建议→半自动；容量规划；成本与选择联动；企业 SSO/RBAC | L4 + L3 闭环 | 可运营、可问责 |

新引擎一律走：Adapter 契约 → 兼容矩阵 → 真机 e2e → 再进入 L3 候选集。

## 9. 成功标准（产品级）

| 维度 | 可验收结果 |
|------|------------|
| 定位清晰 | 客户理解「引擎算数、Nebula 管家」，不期待训练或公有云聚合 |
| L1 | 同一业务代码切换已支持引擎，API/错误/流式行为通过契约套件 |
| L2 | 多池混部可部署；不支持的拓扑被显式拒绝；故障不跨池蔓延 |
| L3 | 给定约束能出 Top-K；不足数据不瞎选；切换有成本与审计 |
| L4 | SLO 可评估可诊断；成本可归因；配额隔离压测通过 |
| 工程 | 热路径与选择/治理解耦；主轴原则无破坏 |

## 11. 总结

Nebula 的产品定位是 **私有化机房的跨引擎推理控制面**，建设目标是在 L0 底座之上，交付四层统一平台能力：

1. **一致性抽象** — 客户与后端解耦
2. **异构调度与资源** — 吃尽并隔离真实算力
3. **智能选择** — 约束下可解释、可回滚的后端方案（含切换成本）
4. **生产运维闭环** — 可观测、可规划、可问责、SLA 可运营

当前版本已具备较强 L0 与部分 L1/L4/L3 雏形（推荐/Canary）；缺口集中在 **L3 成层、L2 池化与拓扑、L1 契约硬化、L4 真机与闭环**。演进应坚持声明式与热路径隔离，用分阶段验收把「工程完成」变成「生产可运营的统一模型服务平台」。

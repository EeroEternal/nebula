## [Unreleased]

### Added
- **Cluster tenant quotas no longer multiply by the Gateway count (issue #68, HA-P2 first slice; measured with a real etcd + 2 gateway processes).** Tenant RPS / concurrency / token / pin limits were per-process counters, so N Gateways enforced N× the configured limit. `NEBULA_GATEWAY_QUOTA_MEMBERS=N` (default `1`, behaviour unchanged) declares how many Gateways share the quota and every replica enforces `limit / N` (`nebula_common::quota_shard`, floor division, remainder deliberately unused), so the shards summed over the declared members can never exceed the configured limit and the admission path still does zero etcd/Postgres I/O. Consequences, all deliberate: the member count is a deployment invariant (scaling Gateways without bumping it re-introduces oversell), a `limit < N` tenant is denied rather than oversold, and a dead Gateway's shard is not redistributed. Also fixed while making the accounting true: the tenant `ConcurrencyGuard` was released when the handler returned, not when the stream finished, so a streaming request held a concurrency slot only until first byte — it is now moved into the SSE forwarding task on all three entry points (`/v1/chat/completions`, `/v1/responses`, `/v1/messages`). Docs: [`docs/dev/queue-admission.md`](docs/dev/queue-admission.md) §7.1–7.2, [`docs/arch/ha.md`](docs/arch/ha.md) §4.1, [`docs/manual/deployment.md`](docs/manual/deployment.md) §7.9. Measured with [`scripts/ha_quota_drill.sh`](scripts/ha_quota_drill.sh) (repo-grade etcd 3.7 + 2 real Gateway processes + a mock engine): a 10/min tenant quota admits 20 across two replicas at `members=1` (the old behaviour) and exactly 5 + 5 at `members=2`, the rest `429 tenant_rps_exceeded`; a streaming request holds its concurrency slot for its whole life and the other replica keeps its own shard; a `limit < N` tenant is denied on both. Evidence and the non-covered list: [`docs/dev/ha/quota-drill.md`](docs/dev/ha/quota-drill.md). Re-verified on 3 real Railway Sandbox VMs (3-node etcd + 2 Gateways + mock engine on separate machines): same 20-vs-10 numbers, plus `limit < members`, a killed etcd member (n2 takes over, both Gateways keep serving, n1 rejoins) and a killed/restarted Gateway. That drill found a real defect: with a dead etcd member the per-request `/tenants/{id}` read failed and the Gateway **served without quota, silently** - a quota bypass. It now retries once and, if every attempt fails, still serves but increments `nebula_gateway_tenant_lookup_failed_total` and warns (measured: exactly 2/min with a dead member and counter 0; the counter climbs only when etcd has no quorum at all). The per-request tenant read itself remains the HA-P1 gap - a background snapshot is not implemented. Report: [`docs/dev/ha/railway-drill.md`](docs/dev/ha/railway-drill.md). Not delivered: automatic membership discovery / re-shard and unused-shard redistribution (needs the `/gateways/` lease registry).
- **TokenSpeed is a first-class engine, and four TokenSpeed-derived designs reached the routing path (2026-10-26; unit-tested, not yet rig-verified).** `"tokenspeed"` now passes `validate_engine_type`, carries a static capability (OpenAI surface, no LoRA, waiting/running/prefix-hit observability), a default `tokenspeed-nvidia-cuda` compat rule, an arg encoder (`block_size` → `--prefix-granularity`, MTP → `--speculative-algorithm NEXTN`), a node executor (`--tokenspeed-*`, local `tokenspeed serve` or docker with container reuse) and a k8s pod path, and `parse_tokenspeed_metrics_text` reads the `tokenspeed:` namespace. Borrowed from TokenSpeed's scheduler/KV model: (1) **block granularity** — `PromptHasher`, `is_short_prompt`, `saved_prefill_tokens` and `PrefixAffinity`'s block→token cost all follow the model's real `block_size` instead of a hardcoded 16, so an MLA model at 64 is no longer mis-bounded and 4× under-counted; (2) **`pd_split` remote hits** — `/lookup` parsing is now one `nebula_common::max_matched_tokens_for_model` shared by controller and router (the router's copy was model-blind, so two models on one LMCache controller could credit each other's cache), and a pure `lm://` hit counts `saved_prefill_tokens`; (3) **head-of-line visibility** — `waiting_requests`/`running_requests`/`num_preemptions_total` are scraped and routed on instead of being summed into `pending_requests`: `LeastPending` breaks ties on waiting then KV, `PrefixAffinity` prices a waiting request above a running one and penalises a replica that is preempting, and scale-down prefers the replica with the emptier running batch; (4) **capacity shape** — `estimate_kv_cache_vram_mb` knows full/sliding-window/linear-state layer mixes (`sliding_window_tokens`, `linear_attention_layer_ratio`, `kv_lora_rank`) instead of assuming uniform full attention, and `kv_preemptions_detected` names KV thrash. Also: `TRITON_CACHE_DIR`/`TORCHINDUCTOR_CACHE_DIR` point at the mounted model volume on node containers and k8s pods, so a restart reuses compiled kernels instead of re-JITting the first wave. Design and TokenSpeed analysis: [`docs/dev/tokenspeed.md`](docs/dev/tokenspeed.md).
- **The engine data plane now has one outbound contract (`nebula_common::UpstreamTransport`).** The Gateway's embedded path (`forward_embedded`) and the Router's replica proxy call `execute()` instead of a raw `reqwest` client, so the `xlite-transport` data plane (issue #80, xlite#96) can replace the transport without touching retry, deadline, cancellation or metric semantics — all of which stay with the caller. `UpstreamRequest`/`UpstreamResponse`/`UpstreamBody` carry raw `Bytes` and one typed `UpstreamError` (`InvalidRequest`/`Dns`/`Connect`/`HeaderTimeout`/`Stall`/`BodyIncomplete`/`Reset`/`Cancelled`/`Other`); its metric labels stay the frozen `timeout`/`connect`/`other`, so `nebula_gateway_upstream_error_total{kind}` and `nebula_router_upstream_error_total{kind}` (and the alert rules on them) do not move. One `execute()` is one attempt — no retry, no failover, no hidden redial — and the per-phase budgets (first byte 60 s / idle 120 s / cross-attempt 90 s) and the pre-first-byte replica switch are unchanged. A caller fault (`InvalidRequest`) is now separated from upstream failures: it is not counted in `*_upstream_error_total`, does not mark a healthy replica failed and does not retry another replica (an unbuildable request fails identically everywhere) — it returns 500 instead of an upstream 502/504. Transport selection is `NEBULA_UPSTREAM_TRANSPORT=reqwest|xlite` (default `reqwest`); an unimplemented value fails at startup instead of silently falling back, so an A/B can never end up running the same transport twice. Both `/metrics` endpoints gained the transport counters `nebula_upstream_in_flight` and `nebula_upstream_failed_dial_total` (a field the transport cannot measure is absent, never a fake 0). Breaking (in-tree only): `nebula_gateway::proxy_common::classify_reqwest_error` is gone (use `nebula_common::reqwest_error_kind`) and `nebula-router`'s `AppState.http` was removed.
- **Pin pressure is part of the L1 capacity estimate (Batch 6.5, 2026-10-23).** Pinned KV and the cache working set share one tier and pins cannot be evicted, so a pin budget does not cost extra host memory — it *shrinks the cache*. `KvSharingSpec.pin_budget_gb` declares the reserve per replica (must be smaller than `local_cpu_size_gb`, rejected at write time otherwise, since a reserve ≥ the tier is guaranteed thrash), and the capacity snapshot subtracts it and emits `kv_l1_pin_reserve_high` with the concrete numbers (reserved GB, percent, remaining working set) instead of a bare alarm name. Per-session cost is model-specific (`2 × layers × kv_heads × head_dim × dtype_bytes / TP`; 112 KiB/token for 0.6B fp16), which is why the reserve is declared per deployment rather than derived from a global constant. **Not** a runtime quota: the router still pins whatever it is asked to; LMCache exposes pinned *object counts*, not pinned bytes, so real usage cannot be reported yet.
- **Tool-Pause now pins the session spine in KV L1 (Batch 5.4, rig-verified 2026-10-23).** When the gateway/router observe `finish_reason=tool_calls` themselves (never a client hint), the router pins the first `NEBULA_TOOL_PAUSE_PIN_TOKENS` (default 4096) prompt tokens of that session against `lmcache_controller` `POST /pin`, addressed per replica (`{model_uid}-{replica_id}`). Why it was needed: LMCache's own scheduler lookups *do* pin, but the adapter releases them with `lookup_unpin(req_id)` when the request finishes, so a 2–30 s tool pause is unprotected — measured on 5 GB L1: an unpinned 1.5 k-token prefix is evicted after ~10 GB of churn, a pinned one survives (engine-side `LMCache hit tokens: 1280` after the flood). Design consequence of the measured contract: `/pin` has **no unpin endpoint** — it is a lease released by `pin_timeout_sec` (new `KvSharingSpec.pin_timeout_sec`, default 300 s) or restart, so there is deliberately no renewal/unpin path, and prefixes are chunk-aligned to LMCache's 256 so sub-chunk spines are skipped instead of silently pinning nothing. Counters `nebula_router_tool_pause_pin_total{result=ok|failed|skipped}` + `tool_pause_pinned_tokens_total`; pins are spawned off the response path and never affect a status code. Budget: ~0.11 MB L1 per pinned token (measured), so 4 k tokens ≈ 0.45 GB of L1 — pin pressure is now declared, not assumed.
- **Streaming failures stop looking like success (2026-10-18).** A stream that dies before `[DONE]` now always says so: per-phase deadlines (`NEBULA_PROXY_FIRST_BYTE_TIMEOUT_MS` 60 s, `NEBULA_PROXY_STREAM_IDLE_TIMEOUT_MS` 120 s, cross-attempt `NEBULA_PROXY_FIRST_BYTE_TOTAL_BUDGET_MS` 90 s, no flat total cap), a pre-first-byte gate that buffer the first chunk before committing `200` and retries another replica instead (`503 + Retry-After: 1` when none answers), and one OpenAI-shaped error frame on mid-stream failure — never a fake `[DONE]`. Mid-stream upstream errors used to be swallowed with no log and no counter; they now increment `upstream_stream_error_total`. Both `nebula-router` and `NEBULA_ROUTER_MODE=embedded` follow the same contract. Rig: stalled-before-first-frame replica retried to a healthy one (`http=200`, 201 frames, `first_byte_retry_total=1`); both stalled → `503` in 5.0 s; stall after the first byte → error frame, no `[DONE]`. Client-visible consequence, documented in the deployment manual: response headers now arrive after the first token.
- **Silent degradations are now countable (2026-10-18).** `stage_stats_missing_total{decision="short_bypass"|"prefill_spillover"|"warm_signal_cold"}` and `route_stale_stats_dropped_total` name the three ways pd_split stage routing can degenerate (no `/stats/` pipeline, no fresh stats, warm signal never firing) instead of quietly routing everything to Prefill. The root cause of the warm-signal failures was measured, not guessed: an engine that starts before `lmcache_controller` registers but never reports its KV keys, sticky until restart — so `nebula-node` and the k8s-controller now gate engine/pod launch on the controller's port (`wait_for_lmcache_controller`).
- **KV L1/L2 tiers are declared instead of hardcoded (Batch 6.1, 2026-10-18).** `KvSharingSpec.local_cpu_size_gb / local_disk_path / local_disk_size_gb` map onto LMCache's real knobs (undeclared keeps the historical 5 GB), `NodeStatus` reports host DRAM and the capacity snapshot emits `kv_l1_oversubscribed` when N replicas would overcommit a node — previously every pd_split replica silently reserved 5 GB of host memory that nothing declared or reported.
- **KV cache lifecycle API and hit accounting (Batch 6.3 / 6.4, 2026-10-18).** `nebula-control::LmcacheController` (`/lookup` `/pin` `/clear`, request shapes verified against lmcache 0.5.5) exposed as `POST /api/v2/models/{uid}/cache/{lookup,pin,clear,warmup}`; `warmup` runs a real inference through the router because only an engine can produce KV. `nebula_router_saved_prefill_tokens_total{model_uid}` counts the prefill tokens the *served* replica already held (blocks × 16, conservative: non-selected owners and cold requests count zero); no dollar figure is emitted because no per-model price input exists.
- **pd_split A/B re-measured with both prerequisites satisfied (2026-10-18), and two earlier conclusions corrected.** Same rig, prerequisites met (controller first, `/stats/` readable, `pd_lookup_warm_total=176/600`): replicated 12.89 rps / p50 107 ms / p99 219 ms vs pd_split 10.75 rps / 257 ms / 343 ms — pd_split is behind on all three metrics in the 7B/TP=1/single-node/1:1 configuration. The earlier “8.6× slower (cold-start burst read as warm)” and “p99 −61% (measured while the warm signal was dead)” conclusions are kept as dated corrections in benefit-verification.md; the benefit now narrows to retrievals clearly cheaper than recompute or decoupling prefill/decode failure domains.
- **pd_split v1 finished: API path, benefit A/B, fault injection, allowlist, console (2026-10-13).** Remaining five items closed on the rig. (1) Benefit A/B, client-side through the gateway: warm steady state — throughput parity (27.3 vs 28.7 rps), tail better with pd_split (TTFT p99 572 vs 721 ms, −21%; e2e p99 736 vs 893 ms); wide-prefix cold runs favour replicated (3.15 vs 3.72 rps) because a 1:1 pool split serialises all cold prefill on one replica and TCP retrieval is slower than a local hit — v1 is a tail-latency play, not a throughput one. (2) Fault injection: store killed mid-run and network blackhole both degrade gracefully (0 rejections, ~2× latency, no hangs — client timeouts hold); a long request survives a mid-flight store kill (200, 50 s, recompute); with the store down at boot engines restart 1-3 times and become ready slowly but then serve (0 rejections); with the *controller* down at boot they crash-loop — a deployment ordering constraint. (3)+(4) `validate_pd_split_image` with `NEBULA_APPROVED_PD_IMAGES` (empty list disables pd_split entirely) and a console deploy dialog for replicas/topology/roles/shared-KV. (5) API-path e2e via BFF `POST /api/v2/models/{uid}/start`: precise rejection reasons, allowlist enforcement, and a valid pd_split creating roled pods. Rig fixes on the way: platform-scoped compat rules no longer fire without platform evidence (the ascend deny rule had been rejecting every vllm deployment lacking node inventory), and pod launch-config changes now recreate pods (fingerprint annotation + delete-then-create) — pod specs are immutable, so the previous apply-based path silently kept stale config.
- **pd_split warm signal works end-to-end via the LMCache controller (rig, 2026-10-13).** The blocking finding from the previous round (LMCacheConnectorV1 disables vLLM kv-events, so the P1c index cannot be the warm signal) is resolved with option 1: the router asks the LMCache controller `POST /lookup` for the prompt's token ids, parses the matched-prefix length (handles both the flat and the live `layout_info`-nested response shapes), caches it 2s per (model, first token) and degrades to cold on any error. Engines register via `lmcache_controller_env` — all four mandatory fields (enable, pull :8300, reply :8400, worker ports) — after the reply URL omission crash-looped engines. Counters `pd_lookup_total`/`pd_lookup_warm_total` exposed. Rig result: cold request → prefill (stores 569 tokens), warm request → decode pool with `Retrieved 512/512 tokens (0.027 GB)` and `hit tokens: 512`; routing distribution prefill=1 / decode=2; warm lookups 2/2.
- **pd_split rig end-to-end: blocking finding (2026-10-12).** Deployed a real pd_split model on the rig (prefill GPU0 / decode GPU1, baked image `nebula/vllm:0.23.0-lmcache0.5.5`, `lm://` shared store). Working end-to-end: scheduler projected roles into placements, both planes injected role-correct LMCache env + `--kv-transfer-config` with the shared seed, endpoints registered with `role`, and the shared store served KV (prefill replica retrieved 569/569 tokens). Blocking: with `LMCacheConnectorV1` active the engine logs `LMCache INFO: KV events are disabled.` — LMCache takes over the KV path and stops vLLM's kv-events, so the P1c prefix index receives almost nothing (1 entry, hit_total=0) and cannot serve as the pd_split warm signal; both test requests landed on the prefill pool. Options recorded in pool.md: use LMCache's own lookup/controller API (cleanest), find an LMCache switch that keeps vLLM events on, or drop the warm signal and route by `kv_both`'s retrieve-or-self-prefill behaviour. Also fixed en route: snake_case wire format for role/topology (controller had been silently skipping deployments), controller honouring `spec.docker_image` instead of a hardcoded `:latest`, and pd_split hashing under any strategy.
- **pd_split decode-pool reachability fix (rig verification).** The first implementation keyed "warm" only off session affinity, so cold traffic anchored on a prefill replica and the decode pool was unreachable. The warm signal is now the prefix-index hit — a store-level fact meaning the shared KV already holds the prefix and any decode replica can retrieve it (the multi-owner index for *local* preference inside the decode pool remains v1.1, review #5). Also fixes two rig-caught issues: ReplicaRole/DeploymentTopology now serialize snake_case per the documented contract (the controller had been skipping deployments silently) and the controller honours `spec.docker_image` instead of a hardcoded `:latest` (compat-matrix/baked-digest discipline).
- **pd_split router stage filtering (step 3/5).** When any candidate endpoint declares a role, the router routes cold traffic to the prefill pool (which writes KV into the shared store) and session-continued traffic (session affinity resolving to a decode replica) to the decode pool; an empty role pool falls back to all candidates behind a new `nebula_router_stage_fallback_total{stage=prefill|decode}` counter (surfaced through the BFF prefix-affinity endpoint and the Endpoints console card). Replicated deployments never enter the branch. 3 unit tests cover cold→prefill, session→decode, empty-pool fallback, and the replicated no-op.

- **Benefit verification with client-side metrics (assessment recommendation 3).** 8-round interleaved A/B on the rig (96 prefixes × 2048 tok, C=32 overload, gateway queue ON): cold start — prefix_affinity eliminates 429 rejections (12%→0%) and doubles goodput (11.9→28.7 rps); warm steady state — goodput +23%, client TTFT p99 −7%, e2e p99 −8%. Key honest finding: client-side p99 improvement is smaller than engine-side TTFT improvement (the assessment's warning holds — queue wait dominates tail latency), and warm-state gains are narrower than the earlier cold-only benchmark's +74% claim. Recommendation: implement pd_split v1 (role-aware full-request routing) first, re-verify with this tool, then decide on strict PD. Full data in docs/dev/benefit-verification.md.
- **Delivery convergence: deployment manual §7.5-7.8 (assessment recommendation 2).** Version-pinning manifest with per-component upgrade gates (ci.sh / check_lmcache_compat.sh incl. --full on pin changes / kv-events wire recalibration on engine upgrades); the P1c deployment matrix — 11 environment variables across router/indexd/controller with the verified values, the "operational trio" that must hold or affinity silently degrades, and the first-response troubleshooting metric (strategy_fallback_total{no_signal}); etcd snapshot/backup/restore procedure (index deliberately out of scope — rebuildable cache); control-plane and engine upgrade/rollback runbooks (GLIBC build-target note, declarative image switch, post-rollback no_signal spot-check).
- **Doc convergence (credibility batch A4, assessment P1).** README and manual/positioning now state v1.10.0 (was 1.8.0 / 1.4.0 while the workspace is 1.10.0); dev/etcd.md moves `/pools/` from "proposed" to implemented (CRUD exists since v1.8.0); the root DESIGN.md visual spec (OKLch/cyan/glow "Tech Utility", conflicting with the actual calm HSL UI) is archived with a redirect — `docs/design.md` is the sole UI design entry, per the repo's standing convention.
- **Quota semantics boundary (credibility batch A3, assessment P0-1).** queue-admission.md now describes the implemented mechanism accurately (semaphore admission with bounded waiters and a per-tenant WAITER-SHARE cap — not the previously claimed per-tenant round-robin dequeue) and carries an explicit delivery boundary: queue/quota counters are per-Gateway process state, so N gateways ⇒ ~N× the configured limits — "per-Gateway engine protection + tenant fairness" is the honest claim, cluster-level strict quotas are not. A unit test pins the actual fairness semantics (a hot tenant saturating its share gets tenant_queue_full beyond it while another tenant still queues and is admitted).
- **Endpoints console truthfulness (credibility batch A2, assessment P0-4).** The hardcoded `2` protocols and `nominal` mesh-health stat cards are now computed from live endpoint data (distinct api_flavors; health = all-ready → nominal, any not-ready → degraded, no data → unknown). The prefix-affinity card now polls every 10s like the rest of the page and distinguishes fetch failure (router /metrics unreachable) from "affinity not enabled". zh/en strings added.
- **Embedded-router KV-event wiring fixed (credibility batch A1, assessment P0-2).** The gateway's embedded mode started only the four etcd sync loops — the KV-event ingest/sink/TTL runtime lived solely in the standalone router's main, so the prefix index stayed permanently empty in embedded mode while `body_prompt_hashes` kept computing hashes against it (silent no-signal fallbacks). The runtime is now a shared `start_kv_runtime` called by both modes, with an end-to-end consistency test (synthetic PUB→SUB event stream → index populated through the shared runtime). A2-A4 (console truthfulness, quota-semantics boundary, doc convergence) queued in roadmap as the credibility batch; pd_split step-3 implementation deferred until after it.
- **pd_split design v1.1 after independent REWORK review.** Six review findings addressed in pool.md: (1) v1 repositioned as role-aware FULL-REQUEST routing over shared KV — single-request prefill→decode handoff is explicitly v2 open design, not claimed; (2) "store-down = TTFT-only" downgraded to "expected fallback, pending fault injection" (four scenarios: pre-start unreachable, mid-run disconnect, blackhole, mid-transfer) since recompute also raises GPU load; (3) placement/config lifecycle added (Deployment→Scheduler→PlacementAssignment→Node projection, change⇒new version+drain, autoscaling banned for pd_split in v1, scale-down must keep ≥1 prefill+decode); (4) deployment must reference a gate-passed baked image digest (gate's pip-install environment ≠ artifact), full-gate assertion tightened to positive token transfer, conservative KV-compat scope (TP=1, same kv dtype/block size/hardware family; others rejected); (5) P1c single-owner index cannot deliver decode-pool local-hit preference (prefill Stored overwrites the owner) — dropped from v1, multi-owner candidate-scoped index specified as v1.1; (6) per-deployment hash_seed removed — v1 mandates one global seed shared by router and engines, mismatch is visible degradation.
- **`pd_split` topology design (P1c Batch 3 step 2, docs/arch/pool.md).** Role-based placement design anchored entirely to the rig-verified no-NIXL shared-KV form: `ReplicaPlacementSpec.role` (prefill/decode/mixed) + `Deployment.topology=pd_split` + `kv_sharing {remote_url, serde, hash_seed}` + `EndpointInfo.role` (all serde-defaulted, backward compatible); injection mapping reusing the existing kv-events injection point in controller/node; Router v1 semantics = stage detection (session/P1c local hit → decode, else prefill) with role filtering and visible stage-fallback counters; lmcache_server as an operator-managed stack component (etcd-style). Explicit failure semantics (decode-pool loss → prefill fallback; store loss → engine recompute). Implementation touchpoint list included (~2-3 sessions). Awaiting review before step 3 implementation.
- **LMCache upgrade gate (`scripts/check_lmcache_compat.sh`).** Quick mode (no GPU): pinned lmcache installs/imports, `lmcache_server` boots on plain TCP, nebula's config keys still accepted by the schema, `chunk_size` still 256 (the sub-chunk-prompt trap), vLLM still ships the zmq kv-events publisher. `--full` adds the 2-GPU cross-engine proof: producer stores, consumer retrieves over `lm://` TCP, asserting the `Retrieved N/N` evidence. Both modes verified on the rig (8/8). Run it before changing `LMCACHE_PIN` or `VLLM_IMAGE`.
- **LMCache no-NIXL KV transfer WORKS via `lm://` remote store (P1c Batch 3).** Wired the final line: `lmcache_server` (LMCache's own TCP KV storage service) + both engines pointing at `remote_url: lm://localhost:6800`. Verified on the rig with a 681-token prompt: prefiller (GPU0) Stored 681/681 tokens (0.036 GB, 0.93 GB/s) to the remote; decoder (GPU1) hit and Retrieved 512/512 tokens (0.027 GB, 139 ms) over pure TCP, recomputing only the tail — zero NIXL, cross-engine, hardware-neutral. Root cause of the earlier hit=0: prompts shorter than one chunk (chunk_size=256) never register as hits on the consumer's standard lookup path. The no-NIXL PD form for nebula is the shared-KV-store topology (prefill pool writes, decode pool reads, `kv_both` role), which also removes the dependency on vLLM's disagg proxy — routing and role orchestration stay in nebula (P1c index + role-aware placement). Orchestration parameters documented in engines.md §7.4.
- **LMCache PD progress (P1c Batch 3, follow-up).** Upgrading lmcache 0.4.6 → 0.5.5 inside the pinned v0.23.0 image flips the result: the full disagg orchestration now works end-to-end (proxy + GPU0 producer + GPU1 consumer, HTTP 200, correct output, 0.68 s warm) — 0.4.6's no-NIXL crash is fixed upstream. Remaining gap, root-caused to config not code: the actual KV handoff is not wired (`hit tokens: 0`, producer `Controller message sender is not initialized`); `lmcache_rpc_port` builds an IPC socket path and the producer-side LMCache lookup server needs explicit setup per LMCache's disagg-v1 examples. Version pin updated to vLLM v0.23.x + lmcache ≥ 0.5.5.
- **CUDA LMCache-TCP PD live test (P1c Batch 3).** Ran the official disagg_prefill_lmcache_v1 topology on the rig (GPU0 producer / GPU1 consumer + disagg proxy, v0.23.0 image, lmcache 0.4.6, enable_nixl False). Engines boot correctly once LMCache's LocalCPUBackend allocator requirement is satisfied (local_cpu: True — the shipped example only works with nixl on); LMCache's RPC layer is zmq/TCP. First request crashes the consumer EngineCore (`assert lmcache_engine is not None` in request_finished) — the no-NIXL disagg path in lmcache 0.4.6 is not usable as-is; documented next steps (lmcache upgrade, upstream issue, shared-storage fallback). Decision refined: LMCache-only (Mooncake dropped per direction); no Rust rewrite — LMCache is engine-side KV plane, nebula stays control plane + routing.
- **PD transport selection + engine version pin (P1c Batch 3 step 1).** Probed both deployed engine families on the rig: CUDA `vllm/vllm-openai:v0.23.0` and Ascend `vllm-ascend:v0.23.0rc1-a3` ship identical v1 KV-connector module sets, and kv-events (zmq, P1c's foundation) is native on both — P1c is hardware-portable as-is. Decision: LMCache as the PD transfer primary (vLLM's own disagg example path; torch-level transport, GPU-vendor-neutral, same block-hash keyspace as P1c), Mooncake(TCP) as high-throughput alternative; NIXL (Dynamo stack) and p2p_nccl (NVIDIA-only) excluded. Engine version pinned to vLLM v0.23.x — upgrading requires re-running the prefix-affinity wire calibration. Documented in docs/dev/engines.md §7 with the dual-image evidence matrix.
- **Global index service `nebula-indexd` (P1c Batch 2).** Engines publish to one stable zmq endpoint; the service maintains the authoritative prefix index and pushes raw frames (incremental) plus periodic full snapshots (`!reset`/`!snapshot` control topics, reusing the map-form event encoding) to every router sink. Router restarts rebuild from snapshot within one snapshot interval instead of waiting for reuse events; the request hot path never queries the service — on its death routers keep serving from their local replica (visible via fallback counters). Found and worked around another zeromq limitation: 0.4–0.6 PUB sockets never reconnect to a re-bound peer, so pushers rebuild their socket every 30s / per snapshot round (frames buffer in-channel); zeromq upgraded 0.4→0.6. Locally verified: forwarding, restart self-heal, degraded survival, and identical indexes on two routers.
- **Chat-body prefix hashing (P1c Batch 1.1).** `/v1/chat/completions` messages are rendered with the model's `chat_template` (minijinja, transformers-compatible subset incl. `tojson` and whitespace control) and tokenized with `add_special_tokens=false`, token-exact with the engine's `apply_chat_template(tokenize=True)` — verified on the rig: 6 shared-system-prompt chat requests all routed to the holding replica (fallback only on the first). Warm-engine chat A/B (4 prefixes, N=256, C=16): TTFT mean −8.6%, **p99 342 vs 850 ms (−60%)**.
- **Index self-healing verified (P1c Batch 1.2, no code needed).** vLLM v0.23 emits `BlockStored` on cache *reuse* too: after a router restart (index wiped) the index rebuilt within 3 requests (0→9 entries, single `no_signal`); the earlier "warm engines emit nothing" note was a misdiagnosis of the map-form parse bug. `replay_endpoint` replay is now an optional acceleration, not a requirement.
- **P1c: KV-event driven prefix affinity (protocol + hash calibrated against the deployed v0.23.0 image; GPU e2e pending).** New `prefix_affinity` routing strategy routes each request to the replica that already holds its KV prefix. Calibrated against vLLM v0.11 source: engines publish `BlockStored`/`BlockRemoved` KV cache events over ZeroMQ (msgpack; `--kv-events-config` injected by the node and the k8s-controller when `NEBULA_KV_EVENTS_ENDPOINT` is set, topic `{model_uid}/{replica_id}`), the router binds a SUB socket (`NEBULA_ROUTER_KV_EVENTS_BIND`) and maintains an in-memory TTL'd prefix→replica index (rebuildable cache, never in etcd). Request-side hashing replicates vLLM's `sha256_cbor` block-hash chain exactly (block size 16, `NONE_HASH` seed; test vectors cross-checked byte-for-byte against a reference implementation) and tokenizes `prompt`-style bodies via `NEBULA_ROUTER_TOKENIZER_DIR/<model>/tokenizer.json` (chat bodies are not hashed in v1 — chat template gap; they fall back visibly). All fallbacks are counted on `nebula_router_strategy_fallback_total{reason=no_signal|owner_unavailable}`. SGLang has no KV-event publisher — capability gap, falls back visibly.
- **P1c real-machine acceptance PASSED (60001, 8× RTX 5090, 2× vLLM v0.23.0 replicas of Qwen2.5-7B).** Interleaved A/B, cold engines per round, shared-prefix workload (96 prefixes × 2048 tok, C=16, N=512): prefix_affinity vs least_pending = **23.9 vs 13.7 req/s (+74%), TTFT mean 308 vs 569 ms (−46%), p50 144 vs 455 ms (−68%)**; index peaked at ~18.8k entries with fallback only during the cold-start window. Two live-rig bugs fixed on the way: a DashMap get+remove deadlock that froze the whole router on model spec updates, and the engine's actual wire format being msgpack MAP-form events (dict-externalized), which the original tagged-array-only parser silently dropped. Both wire forms are now supported with captured-frame regression fixtures; `nebula_router_prefix_index_entries` exposes index size.
- **Real-machine full-chain validation (60001, 8× RTX 5090, Qwen2.5-7B on v0.23.0):** a live engine with `PYTHONHASHSEED=42` + `sha256_cbor` served a real `/v1/completions` prompt while a zmq subscriber captured its `BlockStored` events. The engine publishes hashes in the external int form (`int.from_bytes(h, "big") & (2^64-1)` — last 8 bytes BE); the prefix index now canonicalizes int/bytes events and request-side 32-byte hashes into one 8-byte keyspace (`kv_hash::external`). Verified numerically: Rust chain over the real tokenizer ids → external form == the engine's published hash, exactly. Both numbers are regression tests.
- **Real-machine calibration (deployed `vllm/vllm-openai:v0.23.0`, no-GPU container):** v0.23 defaults `--prefix-caching-hash-algo` to pickle-based `sha256` and randomizes `NONE_HASH` per process when `PYTHONHASHSEED` is unset — both make cross-replica matching impossible. The node and k8s-controller therefore pin `PYTHONHASHSEED=$NEBULA_KV_HASH_SEED` (default "42") and `--prefix-caching-hash-algo sha256_cbor` on every vLLM replica with events enabled; the router hashes with the same seed. Ground-truth hash vectors were generated by calling the deployed `vllm.utils.hashing` directly, and a real captured zmq msgpack frame pair is now a regression fixture in `kv_events.rs`.
- **Router strategy fallback observability.** Routing strategies that degrade to `least_pending` now expose `nebula_router_strategy_fallback_total{strategy=…,reason="no_signal"|"below_threshold"|"owner_unavailable"}` on the router `/metrics` endpoint (embedded-router mode included). Previously a broken upstream signal — e.g. the `engine_metrics` exact-match bug fixed in `4b64a3f` — silently turned `prefix_cache_aware` / `least_kv_cache` into `least_pending` with no metric, log, or error.

### Fixed
- **A cache hit can never claim the whole prompt, and prompt logprobs never take the cache path (2026-10-26).** The engine must recompute the prompt's last token to produce first-token logits, so `Router::controller_warm_tokens` caps the reusable prefix at `len - 1`, and `pd_warm_cache` stores the exact matched token count instead of a bool (a 2 s TTL hit used to inflate the match to the entire prompt). `body_requires_prompt_logits` (`echo: true` or `prompt_logprobs > 0`) sends the request to the prefill pool, because stored KV pages carry no historical logits. On the deployment contract, `validate_pd_split_with_context` now rejects `topology = replicated` alongside `kv_sharing` instead of returning `Ok(())` and letting the execution plane silently drop the config.
- **Tool-bearing chat bodies are hashable again (2026-10-25, rig E2E).** The router's minijinja subset could not render any chat template that uses `{{ tool | tojson }}` or Python string methods (`message.content.startswith('<tool_response>')`): `chat_ids` returned `None`, so every agent request with tool schemas silently lost its prefix signal (`strategy_fallback{no_signal}`) and the new Tool-Pause pin had no token prefix to pin. `prompt_hash.rs` now registers a jinja2-equivalent `tojson` (json.dumps defaults + HTML escaping) and a Python string-method subset (unmodelled methods raise a named error instead of degrading silently), and this crate builds `serde_json`/`minijinja` with `preserve_order` so tool-schema key order survives like Python dicts. Verified against the engine: the same body tokenizes to 1182 on both sides (engine log `Total tokens 1182`), where it previously produced nothing.

## [1.10.0] - 2026-09-22

### Added
- **Engine-level bounded fair queue admission (P0-#2).** The Gateway now admits requests through a per-model bounded queue before reaching the engine: `NEBULA_GATEWAY_QUEUE_ENABLED`, `NEBULA_GATEWAY_QUEUE_MAX_CONCURRENCY` (in-flight cap per model), `NEBULA_GATEWAY_QUEUE_MAX_WAITERS`, `NEBULA_GATEWAY_QUEUE_TIMEOUT_MS`, `NEBULA_GATEWAY_QUEUE_MODE` (`fair` | `fast_fail`), and `NEBULA_GATEWAY_QUEUE_TENANT_SHARE` (per-tenant share of concurrency). Over-limit requests are rejected with **HTTP 429** instead of being queued unboundedly. The guard spans the whole streaming lifetime, exposes queue depth/in-flight/wait metrics, and separates TTFT into `x-nebula-queue-wait-ms` and `x-nebula-upstream-ttft-ms` response headers. New module `crates/nebula-common/src/queue.rs` (`EngineQueue` / `EngineQueues` / `QueueConfig` / `QueueMode` / `EnginePermit`). Real-machine (RTX 5090, Qwen2.5-7B): engine-side P99 TTFT at concurrency 64 dropped **311 ms → 82 ms (−74 %)** with the same throughput.
- **Multiple engine replicas per model.** `ModelDeployment.replicas` now provisions N engine pods per model (`nebula-{model}` for replica 0, `nebula-{model}-{n}` for the rest), each pinned to a distinct GPU, each registering its own `/endpoints/{model}/{replica}` lease and its own `/stats/{model}/{replica}` from that replica's `/metrics` scrape. Scaling down deletes surplus replicas, terminal pods are recreated, and stale endpoints are dropped when a replica leaves `Running`. Real-machine: 2 replicas, `LeastPending` split 132/128 (≈ 50/50), prefix-cache hit rate 0.92/0.93.
- **Multi-engine alignment (vLLM / SGLang).** Engine metric parsing now lives in `nebula_common::engine_metrics` and is dispatched by `parse_engine_metrics(engine_type, …)`; both the bare-metal node and the Kubernetes controller reuse it instead of keeping private copies. The Kubernetes controller selects image and launch arguments from `ModelSpec.engine_type` (`vllm/vllm-openai:latest` vs `lmsysorg/sglang:latest`) and stamps `engine_type` onto the endpoint. Real-machine: an SGLang pod registers an endpoint with `engine_type: "sglang"`, its `/stats` come from the SGLang parser (`kv_cache_usage` ← `token_usage`), and a chat request through the Gateway returns a valid completion. See [`docs/dev/engines.md`](../../docs/dev/engines.md).
- **`replica_specs[i].node_id` placement.** The Kubernetes controller now honours the per-replica target node (`node_id`, defaulting to the agent's own node) instead of placing every replica on its own `--gpu-node`; with multiple node agents this previously created duplicate pods for the same replica. `replica_specs[i].gpu_indices` was already honoured. Real-machine: `gpu_indices: [1, 3]` pins replica 0 to GPU 1 and replica 1 to GPU 3, and a replica pointed at another node is not created locally.
- **Opt-in embedded router mode.** `NEBULA_ROUTER_MODE=embedded` (`NEBULA_ROUTER_STRATEGY=…`) routes `/v1/chat/completions`, `/v1/responses`, and `/v1/messages` through an in-process router with retry parity and router metrics, removing the separate `nebula-router` hop. Measured effect on P99 is **neutral** (the hop is loopback), so this remains opt-in; `remote` is still the default.
- **Opt-in per-stage latency forensics.** `NEBULA_GATEWAY_STAGE_TIMING=1` logs per-request `recv → body → prep → upstream_hdr → first_chunk` timings correlated by request id. Measured `recv → first_chunk` p99 tracks direct-to-engine TTFT, i.e. the Gateway's own processing overhead is ≈ 0.
- **Operations scripts.** `scripts/nebula-stack.sh` (`start` / `stop` / `status`) brings up and tears down etcd + controller + router + gateway + BFF, and `scripts/verify-embedded-router.sh` verifies the embedded-router path end to end.
- **Design and measurement documents.** New reports under `docs/dev/`: `hw/vllm-serving-perf.md` (engine-boundary latency decomposition, vllm-rs vs Python frontend, plugin-system analysis, zero-code optimization checklist), `landscape.md` (vs NVIDIA Dynamo / llm-d), `direction.md` (strategic and product/performance focus), `queue-admission.md` (P0-#2 design), `prefix-affinity.md` (P1), and `engines.md` (multi-engine alignment).

### Changed
- **Engine metric parsers moved into `nebula-common`.** `parse_vllm_metrics_text` / `parse_sglang_metrics_text` / `parse_engine_metrics` and the `extract_*_metric` helpers now live in `crates/nebula-common/src/engine_metrics.rs`; `crates/nebula-node/src/engine/*` re-use them and the Kubernetes controller scrapes through the same dispatch.
- **Router sync loops promoted into the library.** `crates/nebula-router/src/sync.rs` is public so the Gateway can embed the same loops instead of re-implementing them.

### Fixed
- **Engine metric substring over-match.** `extract_metric` matched metric names by substring, so querying `prefix_cache_*` also picked up `external_prefix_cache_*` counters and corrupted the derived hit-rate. Matching is now by full metric name (`crates/nebula-common/src/engine_metrics.rs`).
- **SGLang would not come up reachable under the Kubernetes controller.** SGLang binds `127.0.0.1` by default (vLLM binds `0.0.0.0`), so the pod IP was unreachable; the controller now passes `--host 0.0.0.0` and `--enable-metrics` (without the latter `/metrics` returns 404).
- **SGLang endpoints expired instead of refreshing.** SGLang's `/health` responds in **> 800 ms**, so the controller's 800 ms readiness probe failed and the `/endpoints/…` lease was left to expire; the probe timeout is raised to 3 s.
- **Kubernetes controller scale-down and pod recovery.** Surplus replicas are deleted on scale-down and pods stuck in a terminal phase are recreated; stale endpoints are removed when a replica is not `Running`.
- **`nebula-stack stop` left replica pods behind.** The script deleted only the replica-0 pod; it now deletes every pod carrying the `nebula.model_uid` label.
- **`Cargo.lock` workspace versions** were out of sync with `Cargo.toml` after the v1.9.2 cut.

### Removed
- _(none)_
